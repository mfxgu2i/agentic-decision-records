# okf-add — 文書の追加・更新ワークフロー

バンドルの知識を1件追加または更新する。本体・索引・履歴をワンセットで更新する。

執筆・更新の規約は本書が正本。バンドル側の`AGENTS.md`は読むための構造説明で、書き方は持たない。
`okf-lint`は本書の規約を検査する側なので、規約を増やすときは本書に書く。

## 守るべき規則

OKF v0.1 仕様。`blob/main`は現在v0.2で条番号がずれるため、参照はコミット固定:
https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/ee67a5ca27/okf/SPEC.md

| 規則 | 根拠 |
|---|---|
| 予約ファイル以外の全.mdがfrontmatterと非空`type`を持つ。`AGENTS.md`/`CLAUDE.md`は運用ファイルで対象外、索引にも載せない | §9 適合条件 |
| 予約ファイル`index.md`/`log.md`が§6/§7の構造に従う | §9 適合条件 |
| `index.md`のfrontmatterはバンドルルートの`okf_version: "0.1"`宣言のみ | §11 |
| ページ間リンクはバンドルルート絶対パス。`[XXX仕様](/specs/xxx-spec.md)` | §5 推奨 |
| 外部素材に由来する主張に`# Citations` | §8 推奨 |
| `log.md`は`## YYYY-MM-DD`の日付見出しを新しい順。既存行は追記のみ | 運用規約 |
| 追加・更新・改名・削除は本体・ルート索引・`_references/index.md`・`log.md`をワンセットで | 運用規約 |

仕様はリンク切れや索引の欠落を理由にバンドルを拒否してはならないとしている。
運用規約はそれより厳しい取り決めであり、仕様の要求ではない。

## バンドルルートの特定

カレントディレクトリに`index.md`と知識文書ディレクトリがあればそこ。なければGlobで
`**/knowledge/index.md`を探す。ディレクトリ名を`knowledge/`から変えた場合は、
`okf-query`と`okf-lint`のパターンも合わせて更新する。

## 手順

### 1. 収録すべき内容か確認する

収録するのは、コードやREADMEを読めば分かることではなく、そこからは読み取れない情報。
意思決定とその理由、未解決の問題、調査ログ、コードには残らない運用手順を指す。

判定テストは2つ。「根拠はコードのここ」と書けるなら、コードから再現できる内容なので収録しない。
モデルが訓練データとして既に持つ一般知識、たとえばフレームワークの一般的なベストプラクティスも
収録しない。書くのはこのプロジェクト固有の判断・経緯に絞る。

`type: Specification`を付ける場合も、事実の列挙ではなく「なぜその仕様にしたか」を主体に書く。
API・スキーマのように構造化できるものは`_references/`に実体を置き、文書は`resource:`で指す
ポインタと判断・落とし穴に絞る。

該当するのが文書の一部なら、文書ごと保留にせず該当箇所を削るか`_references/`の実体に置き換える。
文書全体が該当するなら追加を保留し、意図をユーザーに確認する。

### 2. トピックの単一性を確認する

複数の主題にまたがっていれば主題ごとに分割し、以降の手順を文書ごとに繰り返す。
判定テストは1つ。frontmatter `description`の一文で言い切れなければ主題が複数ある。
`okf-query`の段階的絞り込みは、1文書が1トピックで完結していることに依存している。

### 3. 置き場所を決める

- ルート`index.md`のセクション構成を見て、内容が合うセクションのトピックディレクトリに置く
- 合うセクションがなければ、トピックディレクトリと索引セクションを新設してよい
- YAML・PDF・画像などの非Markdownは`_references/`に実体を置き、それを説明する .md を
  内容に応じたトピックディレクトリに作る

ファイル名はケバブケース英語に`-spec` / `-procedure`のような種別サフィックスを付ける。
`index.md` / `log.md` は予約済み。

### 4. frontmatter を付ける

```yaml
---
type: <種別>                        # 必須
title: "<表示名>"
description: "<一文の要約>"
resource: <対象資産のURI>            # 実体ファイル・外部資産を説明する文書のみ
tags: [<tag>, ...]
timestamp: <YYYY-MM-DD>T00:00:00+09:00
---
```

- `type`: 内容を表す短い英語で自由に定義してよい。表記ゆれを防ぐため既存語彙をgrepで確認する。
  例: `Decision` / `Specification` / `Investigation` / `Runbook` / `Note` / `Reference`
- `description`: 索引エントリの説明文にそのまま使うので、単独で意味が通る一文にする
- `timestamp`: 日付は推測せず`date +%F`の結果を使う
- `resource`: `_references/`の実体や外部資産を説明する文書のみ。`resource: /_references/xxx.yaml`

### 5. 本文を書く

見出し・リスト・表・コードブロックなど構造的なMarkdownを優先する。
既存コンセプトへの言及はバンドルルート絶対リンク。未執筆の文書へのリンクは張ってよい。

#### Citations

次のいずれかにあたる記述があれば、文書末尾に`# Citations`を置き`[n]`の連番で根拠を列挙し、
本文の該当箇所に`[1]`を添える。判定は`type`ではなく本文の主張で行う:

| 主張の種類 | 出典の書き方 |
|---|---|
| 一次資料に由来する | `_references/`配下の資産、外部URLを挙げる |
| 一次観測に由来する | いつ何を観測したかを書く。実機検証・ログ・DBクエリ結果 |
| 意思決定の経緯 | いつどこで確定したかを書く |
| 断定的な原因説明、外部仕様の挙動 | 一次資料か一次観測で裏づける。無ければ根拠が無いことを明示する |

```
[1] `/_references/menu-api.yaml` — エンドポイント定義の実体
[2] 実機検証(YYYY-MM-DD) — キャッシュヒットの観測結果
[3] 推測。外部仕様としては未確認
```

コードは出典に挙げない。判定は字面ではなく「その主張がコードを読めば再現できるか」で行うため、
パスや関数名を伏せて言い換えても同じ。再現できる主張はCitationsを足さず手順1に戻って見直す。
`_references/`配下の資産と外部URLは、機械可読な定義ファイルであっても一次資料として引用してよい。
「変換規則は`xxx()`にある」のような次にどこを見るかを示すポインタは本文に書いてよい。
案内であって根拠ではないため。ただし短い言及にとどめ、動作の記述そのものを担わせない。
用語定義・方針宣言・チェックリストなど、バンドル内で自己完結する文書には不要。

### 6. 索引を更新する

- ルート`index.md`の該当セクションに、ファイル名順の位置へ挿入する:
  `* [タイトル](/specs/xxx.md) - <frontmatterのdescriptionと同文>`
- `_references/`に置いた資産は`_references/index.md`にも追加する。実体はfrontmatterを持たないため
  説明文は手書きし、説明文書へのポインタを添える:
  `* [xxx.yaml](/_references/xxx.yaml) - <実体の説明>。説明文書は /specs/xxx-spec.md`
- ルート`index.md`には資産を個別に載せず、`* [_references/](/_references/) - …`の
  ディレクトリリンク1本に集約する。`_references/`以外にディレクトリ別`index.md`は置かない

### 7. log.md に記録する

当日の`## YYYY-MM-DD`見出しの下に追記する。見出しがなければ`# Log`の直後に新設する。
日付は`date +%F`の結果を使う。既存行は変更しない。

```
* Creation: [タイトル](/specs/xxx.md) を追加。<一言の背景>
```

### 8. 自己検査

- [ ] コード事実の言い換えや一般知識の解説に留まっていない
- [ ] 構造化できる仕様を散文で写していない。実体は`_references/`に置いたか
- [ ] 主題が1つに収まっている。`description`の一文で言い切れる
- [ ] `# Citations`にコードを出典として挙げていない
- [ ] frontmatterに非空`type`があり、`timestamp`が`+09:00`付きで当日の日付になっている
- [ ] `_references/`に資産を置いた場合、説明文書に`resource:`があり`_references/index.md`にも載せた
- [ ] 索引エントリの説明文がfrontmatter `description`と一致している
- [ ] log.mdに当日の日付見出しで追記した

## 既存文書を更新するとき

手順1の収録範囲の判断基準と手順5の執筆規約は追加時と同じ。次をワンセットで行う:

1. 本文を直す
2. `timestamp`を更新日に打ち直す。据え置くと`okf-lint`がドリフト疑いとして報告する
3. 要旨が変わったなら`description`とルート`index.md`のエントリ説明文を同じ文に直す
4. `resource:`の指す先が変わったなら合わせて直す
5. log.mdに `* Update: [タイトル](/specs/xxx.md) を更新。<何をどう変えたか>` を追記する

## 改名・削除するとき

1. 旧パスをバンドル全体でGrepし、他文書の本文リンクと`resource:`を洗い出す
2. 改名なら参照をすべて新パスへ書き換える。削除なら参照側の記述をどうするかをユーザーに確認する。
   OKFはリンク切れを未執筆の知識として許容するため、機械的には消さない
3. ルート`index.md`のエントリを付け替える。エントリを消すのは削除の場合だけ
4. `_references/`の資産なら`_references/index.md`も同様に直す
5. log.mdに `* Update: … に改名。<背景>` または `* Deletion: … を削除。<背景>` を追記する

## エスカレーション

既存文書との重複が疑われる場合、削除・改名を伴う場合、大幅な書き換えを伴う場合は、
ユーザーに確認してから行う。
