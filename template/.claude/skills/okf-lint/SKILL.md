# okf-lint — バンドル健全性チェック

バンドルを OKF v0.1 の適合条件と `okf-add` の執筆規約に照らして検査する。
機械的な不整合は修正し、内容判断を要するものと、埋めるのに判断が要る欠落は報告にとどめる。

規約の正本は `okf-add`。本書は検査の粒度と重大度だけを持つ。判定基準が要る項目では
`.claude/skills/okf-add/SKILL.md` の該当節を読む。バンドル側の`AGENTS.md`は規約の出典ではなく、
検査対象の運用ファイルでもない。

A群は仕様が要求する適合条件、B群とC群は運用規約に由来する。仕様はリンク切れや索引の欠落を理由に
バンドルを拒否してはならないとしており、この違いが重大度の根拠になっている。

## バンドルルートの特定

カレントディレクトリに`index.md`と知識文書ディレクトリがあればそこ。なければGlobで
`**/knowledge/index.md`を探す。ディレクトリ名を変えた場合は`okf-query`と`okf-add`も合わせて更新する。

検査対象はバンドルルート配下だけ。ワークスペースルート側の`.claude/`や`AGENTS.md`、
コードディレクトリは対象外。

## 検査項目

### A. OKF 適合。違反は必ず修正

1. 予約ファイル以外の全知識文書がパース可能なYAML frontmatterを持つ。
   `AGENTS.md` / `CLAUDE.md` は運用ファイルなので対象外
2. すべてのfrontmatterに空でない`type`がある
3. 予約ファイルの構造。ルート`index.md`のfrontmatterは`okf_version`宣言のみで他の`index.md`には
   無いこと、`index.md`のエントリが`* [タイトル](パス) - 説明`形式、`log.md`の日付見出しが
   `## YYYY-MM-DD`形式。見出しの並び順はC.17で扱い、ここでは直さない

### B. 索引の整合。機械的に修正

4. ルート`index.md`への掲載漏れ。`AGENTS.md` / `CLAUDE.md`、予約ファイル、
   `_references/`配下の実体は対象外
5. 索引エントリの参照先が存在しないもの。ディレクトリを指すエントリはディレクトリの存在で判定する。
   同名・類似名のファイルがあれば改名とみなしてパスを付け替え、無ければ削除せずCとして報告する
6. 索引の説明文とfrontmatter `description`の食い違い。frontmatter側を正とする。
   `description`が欠落または空なら書き換えず、C.15として報告する
7. `_references/index.md`の整合。実体はfrontmatterを持たないため`description`照合は行わず、
   実体の掲載漏れと参照先の実在だけを見る。`_references/`以外にディレクトリ別`index.md`が無いこと

### C. 報告のみ。修正はユーザーに確認

8. バンドル内リンクの切れ。未執筆の知識の可能性があるため削除せず一覧で報告する。
   明らかなパスの誤記のみ修正してよい
9. `[[wikilink]]`や相対パスリンクの混入
10. 概念の重複。相互にリンクして役割を分担している場合は重複としない。および`timestamp`が古いまま
    本文だけ更新されている疑い。後者は`git log -1 --format=%ad -- <file>`と`timestamp`を比較する
11. `# Citations`の欠落。判定は`type`ではなく本文の主張で行う。`okf-add`のCitations節の表に挙がる
    4種の主張があるのに`# Citations`が無い文書を報告する。用語定義・方針宣言・チェックリストなど
    自己完結する文書は対象外
12. `# Citations`はあるが実質的な出典になっていないもの。`[n]`の連番でない、`okf-add`の表の
    どの書き方にも当たらない、が該当する。根拠が無いことを明示した推測は有効な出典なので報告しない
13. 収録方針から外れた文書。判定は`okf-add`手順1の2つのテスト。報告は3類型に分ける。
    コード事実の言い換えに留まるもの、モデルの一般知識の解説になっているもの、構造化できる仕様を
    散文で写しているもの。判定は文書単位で行い、全体として意思決定や落とし穴の要素があれば
    一部に説明的な節があっても報告しない
14. `# Citations`にコードが出典として挙がっているもの。対象はバンドル外のソースコードのパスと関数名。
    `_references/`配下の資産と外部URLは一次資料なので対象外。言い換えていても、主張がコードを読めば
    再現できる内容なら報告する。本文中のナビゲーション目的のポインタは対象外
15. frontmatterの欠落と形式。`description`の欠落、`timestamp`が`YYYY-MM-DDT00:00:00+09:00`形式で
    ないもの、`resource:`の指す実体が存在しないもの。値を推測して埋めない
16. 本文の`[n]`と`# Citations`の番号の対応。片方にしか無い番号を報告する
17. `log.md`の日付見出しが新しい順になっていないもの。並べ替えない。原因はたいてい日付の
    打ち間違いで、並べ替えると誤記が既成事実になるため

## 手順

1. バンドルルート配下を列挙する。.mdはすべて、`_references/`配下は拡張子を問わずすべて
2. A → B → C の順に検査する。A・Bの違反は修正し、Cは報告のみ
3. 結果を報告する。検査ファイル数・違反ゼロの項目・修正した項目・報告事項を伝え、
   Cの各報告にはファイルパスと行番号を添える
4. 修正と報告がどちらも0件でなければ、`log.md`の当日の`## YYYY-MM-DD`見出しの下に1行追記する。
   見出しが無ければ`# Log`の直後に新設する。日付は`date +%F`の結果を使う。既存行は変更しない。
   どちらも0件なら追記しない

```
* Lint: <N> ファイル検査、修正 <M> 件、報告 <K> 件。<概要>
```
