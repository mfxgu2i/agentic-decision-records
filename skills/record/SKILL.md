# record — 決定・手順・未解決の問題の記録

`docs/records/` の記録を書き、直し、片付ける。本体と索引をワンセットで更新する。
`docs/` のほかの文書には触れない。

何を残すかはユーザーが決める。このスキルはユーザーに頼まれたときだけ使い、頼まれていない記録を自分の判断で足さない。

## 進む先を決める

頼まれたことに応じて、次の手順へ進む。

| 頼まれたこと | 進む先 |
|---|---|
| 記録の仕組みの導入、セットアップ | 手順0だけ |
| 新しく残す | 手順0から手順6まで |
| 決定を変える、取りやめる | 「ADRを置き換える」。そのあと手順6 |
| runbookやissueの内容を直す、消す | 「runbookとissueを直す・消す」。そのあと手順6 |
| issueが解決した | 「issueを閉じる」。そのあと手順6 |

## 0. 準備を確かめる

このスキルは、次の2つが揃っていることを前提にする。記録を書く前に確かめ、揃っていれば何もせず手順1へ進む。
「記録の仕組みを導入して」「セットアップして」と頼まれたときは、この節だけを行う。

| 前提 | 無いときに行うこと |
|---|---|
| `docs/records/index.md` | 下の内容で作る。`<プロジェクト名>` は、`AGENTS.md` やREADMEの見出しにあるプロジェクト名に置き換える。分からなければユーザーに聞く |
| `AGENTS.md` の末尾にある「プロジェクトの記録」の節 | このスキルと同じディレクトリにある `AGENTS-md-section.md` の中身を、一字一句そのまま `AGENTS.md` の末尾に足す。`AGENTS.md` が無ければ、先頭にプロジェクト名の見出しと説明を1行書いて作る |

```markdown
# <プロジェクト名> の記録

## ADR

## Runbook

## Issue
```

- 既にある内容は書き換えない。`AGENTS.md` には末尾に足すだけにする
- 導入を頼まれたときは、確かめずに足してよい。記録を頼まれた流れで節を足すことになったときは、足す前にユーザーに確かめる
- 節の末尾にある `@docs/records/index.md` の行は、コードブロックやバッククォートで囲まずに書く。この1行が索引を毎セッション読み込ませる。囲むと読み込まれない
- 作業ディレクトリかその上位に `CLAUDE.md`、`.claude/CLAUDE.md`、`CLAUDE.local.md` のいずれかがあると、Claude Codeは `AGENTS.md` を読まない。その場合は進める前にユーザーに伝える。`CLAUDE.md` に `@AGENTS.md` の1行があれば読まれるので、問題ない。ホームディレクトリの `~/.claude/CLAUDE.md` は関係しない
- 置いたあと、新しいセッションで「記録の索引には何が載っている？」と聞けば索引の内容が返る。この確認はユーザーに頼む
- コミットはしない

## 1. 記録するかを確かめる

次の2つをどちらも満たすものを記録する。

| 条件 | 意味 |
|---|---|
| 次の作業を変える | 知らないと、次に作業する人やエージェントが判断を誤る |
| 長く効く | 今の作業が終わったあとも有効であり続ける |

次のものは記録しない。頼まれた内容が当たる場合は、書かずに理由を伝える。

| 記録しないもの | 扱い |
|---|---|
| 仕様書、設計書、計画書 | プロジェクトが選んだ方法で管理する |
| コードやgitの履歴から分かること | 書かない。コードが正 |
| フレームワークの一般的な使い方など、モデルが既に知っていること | 書かない |
| 個人の好み、進行中の作業の状況 | ハーネスのメモリ機能に任せる |
| 担当や期限を管理したい作業 | 課題管理ツールに置く |

## 2. 既存の記録を探す

索引を確認し、異なる表記でも `docs/records/` を検索する。

| 見つかったもの | 進む先 |
|---|---|
| 同じ主題のrunbookやissue | 新規作成せず、「runbookとissueを直す・消す」でそれを更新する |
| 同じ主題のADR、または矛盾するADR | 書き換えない。ユーザーに確認したうえで「ADRを置き換える」へ進む |
| 何も無い | 手順3へ進む |

## 3. 種類を選ぶ

記録は、次の3つの問いのどれかに答えるものに限る。

| `type` | 答える問い | 選ぶ条件 | 置き場所 | その後の扱い |
|---|---|---|---|---|
| `adr` | なぜこうなっているのか | 複数の選択肢からひとつを選んだ。直さずに受け入れると決めた制約もここに入る | `adr/NNNN-<kebab-case>.md` | 書き換えない。変えるときは新しいADRで置き換える |
| `runbook` | どうやるのか | 繰り返し行う作業の手順。コードやスクリプトになっていない手作業と、その順序 | `runbooks/<kebab-case>.md` | 実行して手順が違っていたら直す。作業自体がなくなったら消す |
| `issue` | 何が未解決なのか | 解決する意思のある問題、まだ決まっていない論点 | `issues/<kebab-case>.md` | 解決したら削除する。決定事項があればADRに記録する |

1件に書くのは、ひとつの決定かひとつの主題。`description` に読むべきタイミングと結論を書き切れなければ分ける。
ファイル名は英語のケバブケース。ディレクトリが無ければ作る。

### どの種類にも当たらないとき

無理にいずれかに分類しない。記録する前に、本当に記録が必要かをユーザーに確認する。確認時には次の3点を伝える。

1. 3つの問いのどれにも答えていないと判断した理由
2. 代わりの置き場の候補
3. それでも残すなら、どの問いに答える記録として言い直せるか

| 内容 | 代わりの置き場 |
|---|---|
| 特定のコード箇所に結びつく落とし穴や注意 | そのコードのコメント。踏む場所のそばに置く |
| 調査の結果 | 方針が決まったならadrの背景、対処が残っているならissue |
| 外部の情報の在りか、環境についての事実 | README か `AGENTS.md` |
| 個人の好み、進行中の作業の状況 | ハーネスのメモリ機能 |

ユーザーが必要だと答え、3つの問いのいずれかに言い換えられたら、その種類で記録する。
言い直せなければ書かない。種類を足すかどうかはユーザーの判断に委ねる。

## 4. 本体を書く

### adr

番号は `adr/` 内の最大の番号に1を足し、4桁でゼロ埋めする。最初の1件は `0001`。

```markdown
---
type: adr
description: "<読むべきタイミング。結論を一言>"
status: accepted
date: <YYYY-MM-DD>
---

# <結論を言い切る一文>

## 背景

<なぜ決める必要があったか。制約と、検討して選ばなかった選択肢とその理由>

## 決定

<何を決めたか>

## 影響

<この決定で楽になること、引き受ける不利益、今後の作業で守ること>
```

- 見出しは「〜する」「〜しない」と結論を言い切る。「〜について」にしない
- 理由や却下した選択肢が会話から読み取れないときは、推測で埋めずユーザーに聞く

### runbook

```markdown
---
type: runbook
description: "<どの作業のときに使うか。手順の要点を一言>"
date: <YYYY-MM-DD>
---

# <作業名>の手順

<いつ使うか。始める前に必要なもの>

## 手順

1. <やること。順序や値に理由があれば短く添える>

## 確認

<終わったことを何で確かめるか>
```

スクリプトやコマンド一発で済む作業は、runbookにせずそのスクリプトを指すだけでよい。

### issue

```markdown
---
type: issue
description: "<読むべきタイミング。何が未解決かを一言>"
date: <YYYY-MM-DD>
---

# <何が未解決かを端的に示す一文>

<起きていること、または決まっていないこと>

## 分かっていること

<原因や調査の結果。いつ、何で確かめたか。確かめていない推測は推測と書く>

## 当面の扱い

<回避策。この問題に触れる作業での注意>
```

### 共通

| 項目 | 規約 |
|---|---|
| `description` | 索引にそのまま載る。2文で書く。1文目は、どんな作業の前に読むべきか。2文目は、結論を一言。全体で100字ほどに収める |
| `date` | adrは決めた日、issueは最後に内容を直した日、runbookは最後に手順どおり実行して確かめた日。まだ実行していないrunbookには書いた日を入れ、初回の実行で確かめたら打ち直す。`date +%F` の結果を使い、推測しない |
| 本文中の日付 | 「先週」「来月」のような相対表現は絶対日付に直す。日まで分からなければ、分かる粒度の年月で書く |
| 事実と推測 | 確かめた事実と、そこからの推測を分けて書く。設定値があることと、その設定どおりに動くことは別の主張 |
| コードへの言及 | 次にどこを見ればよいかの案内として、パスや関数名に短く触れる。動作の説明をコードの写しで埋めない |
| リンク | ほかの記録へは相対パスで張る。`[CDN経由にした決定](../adr/0003-xxx.md)` |

`description` は、エージェントが読む記録を選ぶ手がかりになる。1文目が無いと、どの作業で読むべきかが分からない。
2文目があれば、本文を開かなくても索引の1行だけで決定が守られる。

| 悪い例 | 良い例 |
|---|---|
| 予約データの保存方式についての決定 | 予約の保存、一覧、変更、キャンセルの機能を追加する前に読む。正式な記録先は店舗の紙の台帳で、サイトはメールを送るだけ |
| リリース手順 | 新しいバージョンをリリースするときに使う。テストが通るまでタグをpushしない |

## 5. 索引を更新する

`docs/records/index.md` の `## ADR`、`## Runbook`、`## Issue` のいずれかに1行足す。
adrは番号順、それ以外はファイル名順。

```
- [<本体の見出し>](adr/NNNN-xxx.md) — <descriptionと同文>
```

索引はエージェントのコンテキストに常時読み込まれる。次の2点を守る。

- 載せるのは今有効な記録だけ。置き換え済みのadrは載せない
- 全体で200行以内に保つ。150行を超えたら、使われなくなったrunbookや片付いたissueの整理をユーザーに提案する

## 6. 確かめる

- [ ] 手順1の2条件を満たし、「記録しないもの」に当たっていない
- [ ] 3つの問いのどれかに答えている
- [ ] 1件に主題がひとつで、`description` が読むべきタイミングと結論の2文になっている
- [ ] 確かめた事実と推測が区別されている
- [ ] 索引の行が、本体の見出しと `description` に一致している
- [ ] `status: superseded` でない全記録が索引に載っていて、索引のリンク先がすべて実在する

最後の項目は今回作成した記録だけでなく、`docs/records/` 全体を対象に確認する。手作業で生じた不整合もここで修正する。

## ADRを置き換える

記録したADRの本文は書き換えない。例外はリンクの張り替えだけで、決定の内容に関わる記述は変えない。

1. 新しいADRを作成する。背景に旧ADRへのリンクと、変更する理由を書く
2. 旧ADRのfrontmatterに `status: superseded` と `superseded_by: NNNN-xxx.md` を追加する。`description` は、経緯を知りたいときに読むものだと分かる文に直す。本文は変更しない
3. 索引から旧ADRの行を削除し、新しいADRの行を追加する
4. 旧ADRのパスを検索し、ほかの記録から参照されていれば、リンクを新しいADRに張り替える。runbookやissueは、記述も新しいADRに合わせて直す

代わりを決めずに取りやめる場合も同じ手順を踏む。取りやめたことと理由を新しいADRとして書く。

## runbookとissueを直す・消す

| 操作 | 手順 |
|---|---|
| 更新 | 本文を直し、`date` を打ち直す。見出しや `description` が変わったら索引の行も同じ文に直す |
| 削除 | ファイルを削除し、索引から外す。履歴はGitに残る。旧パスを検索し、ほかの記録からのリンクを修正する |

## issueを閉じる

片付いたissueは残さない。

1. 片付ける過程で決まったことがあれば、adrを書く。直して終わっただけなら何も書かない
2. issueのファイルを消し、索引から外す
3. 旧パスを検索し、ほかの記録からのリンクを修正する

## ユーザーに確かめる場面

- 頼まれた内容が手順1の条件を満たさない、または「記録しないもの」に当たる
- 頼まれた内容が3つの問いのどれにも答えていない
- 有効なadrと矛盾する、または既存の記録と重複しそう
- adrの理由が分からない
- runbookやissueを消す
