# record

`docs/records/` にある記録を書き、直し、片付ける。記録の本体と索引 `docs/records/index.md` は、いつも一緒に更新する。
`docs/` のほかの文書には触れない。

索引は `AGENTS.md` から毎セッション読み込まれ、チーム全員のエージェントのコンテキストに入る。エージェントは索引の1行を見て記録を読むかを決め、選んだ記録を全文読む。
このスキルの規約は、ほとんどがこの使われ方から来ている。全員のコンテキストに入るので、ユーザーに頼まれたものだけを書く。索引の1行で選ばれるので、1件に1つの主題に絞る。常時読み込まれるので、索引には有効な記録だけを載せる。

## 操作を決める

まず依頼から操作を決め、その操作のファイルだけを読む。ほかの操作のファイルは読まない。

| 依頼の例 | 操作 | 読むもの |
|---|---|---|
| 「記録の仕組みを導入して」 | 導入 | `references/setup.md` |
| 「残しておいて」「ADRにして」「手順を残して」「issueとして書いておいて」 | 新しく残す | 下の「新しく残す」。種類が決まったら `references/<type>.md` の「書く」 |
| 「この方針はやめる」「〜に変えることにした」 | ADRを置き換える | `references/adr.md` の「置き換える」 |
| 「手順が変わった」「この作業はもうしない」 | runbookを直す・消す | `references/runbook.md` の「直す・消す」 |
| 「issueに分かったことを足して」「issueが片付いた」 | issueを直す・閉じる | `references/issue.md` の「直す・閉じる」 |

依頼の言葉と実際の操作は、ずれることがある。既存の記録を確かめてから操作を確定する。

| 確かめた結果 | 確定する操作 |
|---|---|
| 「残しておいて」の主題に、同じ主題のrunbookやissueが既にある | そのrunbookやissueを直す |
| 「残しておいて」の内容が、有効なADRと同じ主題か、矛盾する | ユーザーに確認したうえで、ADRを置き換える |
| 決定を変えると言われたが、元の決定がADRに無い | 新しく残す。種類はadr |
| 直す・閉じると言われた記録が見つからない | 何もせず、見つからないことをユーザーに伝える |

どの操作でも、最後に「確かめる」を行う。

## 新しく残す

### 1. 準備を確かめる

`docs/records/index.md` があり、`AGENTS.md` に `@docs/records/index.md` の行があるかを確かめる。
どちらかが欠けていれば、`references/setup.md` に従って用意してから進む。

### 2. 記録するかを確かめる

次のものは記録しない。頼まれた内容が当たる場合は、書かずに理由を伝える。

| 記録しないもの | 扱い |
|---|---|
| コードやgitの履歴から分かること | 書かない。コードが正 |
| フレームワークの一般的な使い方など、モデルが既に知っていること | 書かない |
| 個人の好み、進行中の作業の状況 | ハーネスのメモリ機能に任せる |
| 担当や期限を管理したい作業 | 課題管理ツールに置く |

### 3. 既存の記録を探す

索引を確認し、表記を変えながら `docs/records/` も検索する。同じ主題の記録が2件あると、どちらを信じるべきかが分からなくなるため。
同じ主題の記録が見つかったら、「操作を決める」の2つ目の表に従って操作を切り替える。

### 4. 種類を選ぶ

記録は、次の3つの問いのどれかに答えるものに限る。

| `type` | 答える問い | 選ぶ条件 |
|---|---|---|
| `adr` | なぜこうなっているのか | 複数の選択肢からひとつを選んだ。直さずに受け入れると決めた制約もここに入る |
| `runbook` | どうやるのか | 繰り返し行う作業の手順。コードやスクリプトになっていない手作業と、その順序 |
| `issue` | 何が未解決なのか | 解決する意思のある問題、まだ決まっていない論点 |

1件に書くのは、ひとつの決定かひとつの主題。読むべきタイミングを `description` の1文で言い切れなければ分ける。

#### どの種類にも当たらないとき

無理に分類しない。「その他」の種類を作ると、迷った内容が集まって記録が増え続けるため。
記録する前に、本当に記録が必要かをユーザーに確認する。確認では次の3点を伝える。

1. 3つの問いのどれにも答えていないと判断した理由
2. 代わりの置き場の候補
3. それでも残すなら、どの問いに答える記録として言い直せるか

| 内容 | 代わりの置き場 |
|---|---|
| 特定のコード箇所に結びつく落とし穴や注意 | そのコードのコメント。踏む場所のそばに置く |
| 調査の結果 | 方針が決まったならadrの背景、対処が残っているならissue |
| 外部の情報の在りか、環境についての事実 | README か `AGENTS.md` |
| 個人の好み、進行中の作業の状況 | ハーネスのメモリ機能 |

ユーザーが必要だと答え、3つの問いのいずれかに言い換えられたら、その種類で記録する。
言い直せなければ書かない。種類を足すかどうかはユーザーの判断に委ねる。

### 5. 本体を書き、索引に足す

選んだ種類の `references/<type>.md` の「書く」に従って本体を書く。ファイル名は英語のケバブケースにし、ディレクトリが無ければ作る。

続けて `docs/records/index.md` の `## ADR`、`## Runbook`、`## Issue` のいずれかに1行足す。adrは番号順、それ以外はファイル名順。

```
- [<本体の見出し>](adr/NNNN-xxx.md) — <descriptionと同文>
```

索引は全体で200行以内に保つ。150行を超えたら、使われなくなったrunbookや片付いたissueの整理をユーザーに提案する。

## 全種類に共通する規約

| 項目 | 規約 |
|---|---|
| `description` | 索引にそのまま載る。どんな作業の前に読むべきかを、1文で書く。長くても60字に収める |
| `date` | 種類ごとの意味は `references/<type>.md` にある。`date +%F` の結果を使い、推測しない |
| 本文中の日付 | 「先週」「来月」のような相対表現は絶対日付に直す。日まで分からなければ、分かる粒度の年月で書く |
| 事実と推測 | 確かめた事実と、そこからの推測を分けて書く。設定値があることと、その設定どおりに動くことは別の主張 |
| コードへの言及 | 次にどこを見ればよいかの案内として、パスや関数名に短く触れる。動作の説明をコードの写しで埋めない |
| リンク | ほかの記録へは相対パスで張る。`[CDN経由にした決定](../adr/0003-xxx.md)` |

`description` は、エージェントが読む記録を選ぶ手がかりになる。何が書いてあるかではなく、いつ読むべきかを書く。
結論は見出しが伝えるので、`description` で言い直さない。索引は毎セッション読み込まれるので、短いほどよい。

| 悪い例 | 悪い理由 | 良い例 |
|---|---|---|
| 予約データの保存方式についての決定 | いつ読むべきかが分からない | 予約の保存、一覧、変更、キャンセルの機能を追加する前に読む |
| 予約はDBに保存せず、メール通知だけにする | 見出しの言い直しになっている | 同上 |

## 確かめる

- [ ] 新しく残したなら、手順2の2条件を満たし、3つの問いのどれかに答えている
- [ ] 1件に主題がひとつで、`description` が読むべきタイミングを1文で言い切っている
- [ ] 確かめた事実と推測が区別されている
- [ ] 索引の行が、本体の見出しと `description` に一致している
- [ ] `status: superseded` でない全記録が索引に載っていて、索引のリンク先がすべて実在する

最後の項目は今回触った記録だけでなく、`docs/records/` 全体を対象に確認する。手作業で生じた不整合もここで直す。

## ユーザーに確かめる場面

- 頼まれた内容が手順2の条件を満たさない、または「記録しないもの」に当たる
- 頼まれた内容が3つの問いのどれにも答えていない
- 有効なadrと矛盾する、または既存の記録と重複しそう
- adrの理由が分からない
- runbookやissueを消す
