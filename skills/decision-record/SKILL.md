# decision-record

`docs/decisions/` にある決定記録を作成・置き換えします。決定記録の本文ファイルと索引 `docs/decisions/index.md` は、必ず一対で更新します。
`docs/` 内のほかのドキュメントには関与しません。

索引は `AGENTS.md` から毎セッション読み込まれ、このリポジトリで作業するエージェントのコンテキストへ入ります。エージェントは索引の記述から関連する決定記録を判断し、必要な決定記録の本文を全文読み込みます。
ユーザーから明示的に依頼された決定事項のみを記録します。また、索引の1行で参照要否を判断できるよう1ファイルにつき1つの決定事項に絞り込み、常に有効な決定記録のみを索引に掲載します。

## 操作を決める

依頼内容から実行する操作を判断し、その操作に必要な参照ファイルのみを読み込みます。

| 依頼の例 | 操作 | 参照ファイル |
|---|---|---|
| 「残しておいて」「決定として残して」 | 決定記録の作成 | 下記の「記録を作成する」手順と、`references/decision.md` の「書く」 |
| 「決まるまでこうしておく」「当面はこうする」 | 暫定の決定記録を作成 | 下記の「記録を作成する」手順と、`references/decision.md` の「書く」 |
| 「この決定はやめる」「〜に変えることにした」「方針が決まった」 | 決定記録の置き換え | `references/decision.md` の「書く」と「置き換える」。索引の行書式は「記録を作成する」の手順5 |

依頼時の表現と実際の操作が一致しない場合があります。既存の決定記録と索引を確認したうえで、操作を確定します。

| 確認結果 | 確定する操作 |
|---|---|
| 依頼内容が、すでに索引にある有効な決定記録と同じ主題、あるいは矛盾している | ユーザーに確認したうえで、該当する決定記録を置き換える |
| 暫定の決定記録における論点について方針が決まった | 該当する暫定記録を、accepted の決定記録で置き換える |
| 変更対象として指定された決定事項が記録に見当たらない | 新規の決定記録として作成する |

どの操作を行った場合でも、最後に「整合性の確認」を実施します。

## 記録を作成する

### 1. 前提条件を確認する

`docs/decisions/index.md` が存在し、`AGENTS.md` またはハーネスが読み込む指示ファイルに `@docs/decisions/index.md` の記述があるか確認します。
いずれかが不足している場合は、ユーザーへ事前に確認することなく `references/setup.md` に従って準備したうえで作業を進めます。追加した内容は作業完了時にユーザーへ報告します。

### 2. 記録すべき内容か判定する

記録対象は、プロジェクトにおける決定事項とその理由のみです。ほかに正本の置き場がある情報はそちらへ委ね、決定記録には記載しません。
依頼内容が以下の項目に該当する場合は作成を見送り、その理由と本来の置き場をユーザーに伝えます。

| 情報の種類 | 本来の正本の置き場 |
|---|---|
| 個人の好み、作業の進め方 | ハーネスのメモリ |
| コードの意図、変更の経緯 | ソースコード、Git |
| 状態、担当者、期限を持つ項目。未解決の課題や議論中の論点 | 課題管理ツール |
| 作業の手順 | スクリプト、README、運用ドキュメント |
| 常に把握しておくべき前提事項や用語の定義 | `AGENTS.md` や README |
| 仕様書、設計書、開発計画書 | 各プロジェクトに適した管理ドキュメント |
| 言語やフレームワークの一般的な技術知識 | 学習済み知識に委ねる（記録不要） |

該当する項目であっても、その中に決定事項が含まれていれば、その決定事項のみを記録できます。決定事項が含まれていなければ作成しません。

| 依頼内容 | 決定記録として残せるもの |
|---|---|
| 未解決の課題 | 結論が出るまでの間に適用すると合意した方針。provisional として記録する |
| 作業の手順 | その手順を採用すると決めた方針とその理由。手順の詳細は書かない |

### 3. 既存の決定記録を検索する

索引を確認し、表現の揺れも考慮しながら `docs/decisions/` 内を検索します。同一主題の決定記録が複数存在すると、どちらを信頼すべきか判断できなくなるためです。
同一主題の決定記録が見つかった場合は、「操作を決める」の確認表に従って置き換え処理に切り替えます。

### 4. ステータスを選定する

| status | 選定条件 |
|---|---|
| accepted | 確定した決定事項。複数の選択肢から1つを選んだ方針、あえて直さず受け入れた制約、不採用とした方針など |
| provisional | 論点は未決着だが、結論が出るまでの間に守る方針として合意した内容 |

1つのドキュメントに記録するのは1つの決定事項のみです。参照すべきタイミングを description の1文で表しきれない場合は、複数の記録に分割します。

### 5. 決定記録の本文を作成し、索引へ登録する

`references/decision.md` の「書く」に従って本文ファイルを作成します。ディレクトリが存在しない場合は新規作成します。

続けて `docs/decisions/index.md` に1行追加します。番号順を保って追記します。

```
- [<本体の見出し>](NNNN-xxx.md) — <descriptionと同文>
```

索引全体は200行以内を目安に維持します。150行を超えた段階で、廃止可能な古い決定記録がないかユーザーへ見直しを提案します。

## 共通の規約

| 項目 | 規約 |
|---|---|
| description | 索引にそのまま掲載される。どんな作業を行う前に参照すべきかを1文で簡潔に記述する。最大でも60文字程度に抑える |
| date | 決定した日付。推測せず、現在の日付（YYYY-MM-DD）を使用する |
| 本文中の日付 | 「先週」「来月」などの相対的な表現は避け、具体的な日付で記述する。日が特定できない場合は年月で書く |
| 事実と推測の分離 | 検証済みの事実と、そこからの推測を明確に分けて記述する |
| コードへの言及 | 今後の参照案内としてファイルパスや関数名に簡潔に触れるに留める。コードの全文を書き写す実況は避ける |
| 決定記録間のリンク | ほかの決定記録へは相対パスでリンクする。`[CDN経由に変更した決定](0003-xxx.md)` |

description は、エージェントが参照すべき記録を判定するための重要な手がかりです。何が書かれているかではなく、どんな作業の前に参照すべきかを記述します。
結論は見出しで表現されているため、description で同じ結論を重複して言い換える必要はありません。索引は毎セッション読み込まれるため、簡潔であるほど有効です。

| 不適切な例 | 理由 | 適切な例 |
|---|---|---|
| 予約データの保存方式についての決定 | どんな作業の前に参照すべきかが不明瞭 | 予約の保存、一覧、変更、キャンセルの機能を追加する前に読む |
| 予約はDBに保存せず、メール通知だけにする | 見出しの結論をそのまま言い直している | 同上 |

## 整合性の確認

- [ ] 新規作成した決定記録が判定基準を満たし、決定事項とその理由が明確に書かれている
- [ ] 1つのドキュメントに1つの決定事項のみが含まれ、description に参照すべきタイミングが1文で記述されている
- [ ] 確かめられた事実と推測が明確に区別されている
- [ ] 索引の行記述が、決定記録の見出しおよび description と完全に一致している
- [ ] status: superseded でない有効な決定記録がすべて索引に登録されており、リンク先が存在している
- [ ] status: superseded の決定記録が索引から除外されており、superseded_by の指定先が実在している

最後の確認項目は、今回操作した記録だけでなく `docs/decisions/` 全体を対象に確認します。手作業で生じた不整合もあわせて修正します。

## ユーザーに確認すべき場面

- 依頼内容が記録すべき判定基準を満たしていない場合
- すでに有効な決定記録と矛盾する、または重複する恐れがある場合
- 決定に至った具体的な理由が確認できない場合
- 暫定の決定記録において、どのような条件や論点が決着した際に見直すべきかが明確でない場合
