# decision-record

`docs/decisions/` にある決定を書き、置き換える。決定の本体と索引 `docs/decisions/index.md` は、いつも一緒に更新する。
`docs/` のほかの文書には触れない。

索引は `AGENTS.md` から毎セッション読み込まれ、このリポジトリで作業する全員のエージェントのコンテキストに入る。エージェントは索引の1行を見て決定を読むかを決め、選んだ決定を全文読む。
このスキルの規約は、ほとんどがこの使われ方から来ている。全員のコンテキストに入るので、ユーザーに頼まれたものだけを書く。索引の1行で選ばれるので、1件に1つの決定に絞る。常時読み込まれるので、索引には有効な決定だけを載せる。

## 操作を決める

まず依頼から操作を決め、その操作に要るファイルだけを読む。

| 依頼の例 | 操作 | 読むもの |
|---|---|---|
| 「記録の仕組みを導入して」 | 導入 | `references/setup.md` |
| 「残しておいて」「決定として残して」 | 決定を残す | 下の「残す」と、`references/decision.md` の「書く」 |
| 「決まるまでこうしておく」「当面はこうする」 | 暫定の決定を残す | 下の「残す」と、`references/decision.md` の「書く」 |
| 「この決定はやめる」「〜に変えることにした」「方針が決まった」 | 決定を置き換える | `references/decision.md` の「書く」と「置き換える」。索引の行の書式は、下の「残す」の手順5 |

依頼の言葉と実際の操作は、ずれることがある。既存の決定を確かめてから操作を確定する。

| 確かめた結果 | 確定する操作 |
|---|---|
| 「残しておいて」の内容が、有効な決定と同じ主題か、矛盾する | ユーザーに確認したうえで、その決定を置き換える |
| 暫定の決定の論点について、方針が決まったと言われた | 暫定の決定を、`accepted` の決定で置き換える |
| 変えると言われた決定が記録に無い | 新しく残す |

どの操作でも、最後に「確かめる」を行う。

## 残す

### 1. 準備を確かめる

`docs/decisions/index.md` があり、`AGENTS.md` か、ハーネスが読む指示ファイルに `@docs/decisions/index.md` の行があるかを確かめる。
どちらかが欠けていれば、`references/setup.md` に従って用意してから進む。

### 2. 記録するかを確かめる

記録するのは、プロジェクトで合意した決定とその理由だけ。ほかに正本の置き場がある情報は、そこに任せて書かない。
頼まれた内容が次に当たる場合は、書かずに理由と置き場を伝える。

| 情報 | 正本の置き場 |
|---|---|
| 個人の好み、作業の進め方 | ハーネスのメモリ |
| コードの意図、変更の経緯 | コード、テスト、コミットメッセージ |
| 状態、担当、期限を持つもの。未解決の問題、議論中の論点 | 課題管理 |
| 作業の手順 | スクリプトか、READMEや運用の文書 |
| 短く、毎回知っておくべき事実。用語の定義など | `AGENTS.md` かREADME |
| 仕様書、設計書、計画書 | 各プロジェクトに合った方法で管理する文書 |
| フレームワークなどの一般的な知識 | 不要 |

当たる場合でも、そこに合意が含まれていれば、合意だけを決定として残せる。合意が含まれていなければ書かない。

| 頼まれた内容 | 決定として残せるもの |
|---|---|
| 未解決の問題 | 決着するまでの間に守ると合意したこと。`provisional` で書く |
| 作業の手順 | その手順を踏むと決めたことと、その理由。手順の細部は書かない |

### 3. 既存の決定を探す

索引を確認し、表記を変えながら `docs/decisions/` も検索する。同じ主題の決定が2件あると、どちらを信じるべきかが分からなくなるため。
同じ主題の決定が見つかったら、「操作を決める」の2つ目の表に従って操作を切り替える。

### 4. 状態を選ぶ

| `status` | 選ぶ条件 |
|---|---|
| `accepted` | 合意した決定。複数の選択肢からひとつを選んだこと、直さずに受け入れると決めた制約、しないと決めたこと |
| `provisional` | 論点はまだ決着していないが、決着するまでの間に守ることを合意した |

1件に書くのは、ひとつの決定。読むべきタイミングを `description` の1文で言い切れなければ分ける。

### 5. 本体を書き、索引に足す

`references/decision.md` の「書く」に従って本体を書く。ディレクトリが無ければ作る。

続けて `docs/decisions/index.md` に1行足す。番号順に並べる。

```
- [<本体の見出し>](NNNN-xxx.md) — <descriptionと同文>
```

索引は全体で200行以内に保つ。150行を超えたら、取りやめてよい決定がないかの見直しをユーザーに提案する。

## 共通の規約

| 項目 | 規約 |
|---|---|
| `description` | 索引にそのまま載る。どんな作業の前に読むべきかを、1文で書く。長くても60字に収める |
| `date` | 決めた日。`date +%F` の結果を使い、推測しない |
| 本文中の日付 | 「先週」「来月」のような相対表現は絶対日付に直す。日まで分からなければ、分かる粒度の年月で書く |
| 事実と推測 | 確かめた事実と、そこからの推測を分けて書く。設定値があることと、その設定どおりに動くことは別の主張 |
| コードへの言及 | 次にどこを見ればよいかの案内として、パスや関数名に短く触れる。動作の説明をコードの写しで埋めない |
| リンク | ほかの決定へは相対パスで張る。`[CDN経由にした決定](0003-xxx.md)` |

`description` は、エージェントが読む決定を選ぶ手がかりになる。何が書いてあるかではなく、いつ読むべきかを書く。
結論は見出しが伝えるので、`description` で言い直さない。索引は毎セッション読み込まれるので、短いほどよい。

| 悪い例 | 悪い理由 | 良い例 |
|---|---|---|
| 予約データの保存方式についての決定 | いつ読むべきかが分からない | 予約の保存、一覧、変更、キャンセルの機能を追加する前に読む |
| 予約はDBに保存せず、メール通知だけにする | 見出しの言い直しになっている | 同上 |

## 確かめる

- [ ] 新しく残したなら、手順2の基準を満たし、合意した決定が書かれている
- [ ] 1件に決定がひとつで、`description` が読むべきタイミングを1文で言い切っている
- [ ] 確かめた事実と推測が区別されている
- [ ] 索引の行が、本体の見出しと `description` に一致している
- [ ] `status: superseded` でない全決定が索引に載っていて、索引のリンク先がすべて実在する
- [ ] `status: superseded` の決定が索引に残っておらず、`superseded_by` の行き先が実在する

最後の項目は今回触った決定だけでなく、`docs/decisions/` 全体を対象に確認する。手作業で生じた不整合もここで直す。

## ユーザーに確かめる場面

- 頼まれた内容が手順2の基準を満たさない
- 有効な決定と矛盾する、または重複しそう
- 決定の理由が分からない
- 暫定の決定で、どの論点が決着すれば見直すのかが分からない
