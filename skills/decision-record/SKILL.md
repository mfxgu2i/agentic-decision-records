# decision-record

`docs/decisions/` にある決定記録を作成・更新します。決定記録の本文ファイルと索引 `docs/decisions/index.md` は、必ず一対で更新します。
`docs/` 内のほかのドキュメントには関与しません。
決定記録の内容を尋ねられただけの場合は、以下の手順を使わず、索引や本文を直接読んで回答します。

索引は `AGENTS.md` から毎セッション読み込まれ、このリポジトリで作業するエージェントのコンテキストへ入ります。エージェントは索引の記述から関連する決定記録を判断し、必要な決定記録の本文を全文読み込みます。
ユーザーから明示的に依頼された決定事項のみを記録します。また、索引の1行で参照要否を判断できるよう1ファイルにつき1つの決定事項に絞り込み、作業の前に照合すべき決定記録のみを索引に掲載します。

## 操作を決める

依頼内容から実行する操作を判断し、その操作に必要な参照ファイルのみを読み込みます。

| 依頼の例 | 既存の記録 | 操作 | 参照ファイル |
|---|---|---|---|
| 「残しておいて」「決定として残して」 | なし | `accepted` で作成 | 下記の「記録を作成する」と、`references/decision.md` の「本文の雛形」 |
| 「検討中として残して」「決まるまでこうしておく」 | なし | `proposed` で作成 | 同上 |
| 「〜は見送ることにした」 | なし | `rejected` で作成 | 同上 |
| 「候補が増えた」「当面の取り決めを変える」 | `proposed` | 論点を更新 | `references/decision.md` の「議論中の論点」 |
| 「〜に決まった」「〜は見送ることにした」「この論点はもういい」「この件はやめる」 | `proposed` | 論点を決着 | `references/decision.md` の「論点が決着した」 |
| 「〜に変えることにした」 | `accepted` | 置き換え | `references/decision.md` の「本文の雛形」と「決定事項を別の方針に変える」 |
| 「この決定はやめる」 | `accepted` | 廃止 | `references/decision.md` の「決定事項を廃止する」 |
| 「〜は見送ることにした」 | `accepted` | 置き換えか廃止かをユーザーに確認 | 上の2行のどちらか |

依頼時の表現と実際の操作が一致しない場合があります。既存の決定記録と索引を確認したうえで、操作を確定します。

| 確認結果 | 確定する操作 |
|---|---|
| 新規作成の依頼が、すでに索引にある `accepted` の決定記録と同じ主題、あるいは矛盾している | ユーザーに確認したうえで、該当する決定記録を置き換える |
| 「〜に変えることにした」のように、`accepted` の決定記録を変えると明示されている | 確認せずに、該当する決定記録を置き換える |
| 依頼内容が、`proposed` の論点と同じ主題である | 該当する論点を更新するか、決着させる |
| 依頼内容が、`rejected` の案を採用するものである | ユーザーに確認したうえで、新しい `accepted` の決定記録を作成する。`rejected` の記録は変更しない |
| 「〜に決まった」「〜に変えることにした」の対象が記録に見当たらない | 新規の決定記録として `accepted` で作成する |

どの操作を行った場合でも、最後に「整合性の確認」を実施します。

## 記録を作成する

### 1. 前提条件を確認する

`docs/decisions/index.md` が存在し、`AGENTS.md` またはハーネスが読み込む指示ファイルに `@docs/decisions/index.md` の記述があるか確認します。
いずれかが不足している場合は、ユーザーへ事前に確認することなく `references/setup.md` に従って準備したうえで作業を進めます。追加した内容は作業完了時にユーザーへ報告します。

### 2. 記録すべき内容か判定する

記録対象は、プロジェクトにおける決定事項とその理由、そしてまだ結論の出ていない論点です。ほかに正本の置き場がある情報はそちらへ委ね、決定記録には記載しません。
依頼内容が以下の項目に該当する場合は作成を見送り、その理由と本来の置き場をユーザーに伝えます。

| 情報の種類 | 本来の正本の置き場 |
|---|---|
| 個人の好み、作業の進め方 | ハーネスのメモリ |
| コードの意図、変更の経緯 | ソースコード、Git |
| 担当者や期限を持つ作業、方針決定を伴わない不具合 | 課題管理ツール |
| 作業の手順 | スクリプト、README、運用ドキュメント |
| 常に把握しておくべき前提事項や用語の定義 | `AGENTS.md` や README |
| 仕様書、設計書、開発計画書 | 各プロジェクトに適した管理ドキュメント |
| 言語やフレームワークの一般的な技術知識 | 学習済み知識に委ねる |

該当する項目であっても、その中に決定事項や論点が含まれていれば、その部分のみを記録できます。含まれていなければ作成しません。

| 依頼内容 | 決定記録として残せるもの |
|---|---|
| 担当者や期限を持つ作業 | その作業で決めようとしている論点。`proposed` として記録し、担当者と期限は書かない |
| 作業の手順 | その手順を採用すると決めた方針とその理由。手順の詳細は書かない |

### 3. 既存の決定記録を検索する

索引を確認し、表現の揺れも考慮しながら `docs/decisions/` 内を検索します。同一主題の決定記録が複数存在すると、どちらを信頼すべきか判断できなくなるためです。
同一主題の決定記録が見つかった場合は、「操作を決める」の確認表に従って操作を切り替えます。

### 4. ステータスを選定する

`references/decision.md` の「ステータス」から、新規作成で使えるものを選びます。

1つのドキュメントに記録するのは1つの決定事項か論点のみです。参照すべきタイミングを `description` の1文で表しきれない場合は、複数の記録に分割します。

### 5. 決定記録の本文を作成し、索引へ登録する

`references/decision.md` の「本文の雛形」に従って本文ファイルを作成します。ディレクトリが存在しない場合は新規作成します。

続けて `docs/decisions/index.md` に1行追加します。番号順を保って追記します。

```
- [<本体の見出し>](NNNN-xxx.md) — <descriptionと同文>
- [proposed] [<本体の見出し>](NNNN-xxx.md) — <descriptionと同文>
```

`accepted` の行には印を付けません。`proposed` の行には、行頭にステータスを付けます。`rejected`、`deprecated`、`superseded` の記録は索引に掲載しません。

索引全体は200行以内を目安に維持します。150行を超えた段階で、廃止可能な古い決定記録がないかユーザーへ見直しを提案します。

## 共通の規約

| 項目 | 規約 |
|---|---|
| `description` | 索引にそのまま掲載される。どんな作業を行う前に参照すべきかを1文で簡潔に記述する。最大でも60文字程度に抑える |
| `date` | `accepted` か `rejected` になった日付。`proposed` の間は記録を作成した日付。推測せず、現在の日付（YYYY-MM-DD）を使用する |
| 本文中の日付 | 「先週」「来月」などの相対的な表現は避け、具体的な日付で記述する。日が特定できない場合は年月で書く |
| 事実と推測の分離 | 検証済みの事実と、そこからの推測を明確に分けて記述する |
| コードへの言及 | 今後の参照案内としてファイルパスや関数名に簡潔に触れるに留める。コードの全文を書き写す実況は避ける |
| 決定記録間のリンク | ほかの決定記録へは相対パスでリンクする。`[CDN経由に変更した決定](0003-xxx.md)` |

`description` は、エージェントが参照すべき記録を判定するための重要な手がかりです。何が書かれているかではなく、どんな作業の前に参照すべきかを記述します。
結論は見出しで表現されているため、`description` で同じ結論を重複して言い換える必要はありません。索引は毎セッション読み込まれるため、簡潔であるほど有効です。

| 不適切な例 | 理由 | 適切な例 |
|---|---|---|
| 予約データの保存方式についての決定 | どんな作業の前に参照すべきかが不明瞭 | 予約の保存、一覧、変更、キャンセルの機能を追加する前に読む |
| 予約はDBに保存せず、メール通知だけにする | 見出しの結論をそのまま言い直している | 同上 |

## 整合性の確認

プロジェクトのルートで、このスキルに同梱した検証スクリプトを実行します。

```bash
node <このスキルのディレクトリ>/scripts/check-decisions.mjs
```

スクリプトは `docs/decisions/` 全体を対象に、ファイル名、frontmatter、索引の行が食い違っていないかを確かめます。エラーが出た場合は該当箇所を直し、エラーがなくなるまで再実行します。今回操作していない記録のエラーも、手作業で生じた不整合としてあわせて修正します。
Node が使えない環境では、索引の各行がステータス、見出し、description と一致しているかを目視で確認します。

スクリプトでは判定できない次の項目は、内容を読んで確認します。

- [ ] 新規作成した決定記録が判定基準を満たし、決定事項とその理由、または論点と候補が明確に書かれている
- [ ] 1つのドキュメントに1つの決定事項か論点のみが含まれ、description に参照すべきタイミングが1文で記述されている
- [ ] 確かめられた事実と推測が明確に区別されている

## ユーザーに確認すべき場面

- 依頼内容が記録すべき判定基準を満たしていない場合
- すでに索引にある決定記録と矛盾する、または重複する恐れがある場合
- 決定に至った具体的な理由や、案を見送った理由が確認できない場合
- 廃止するのか、別の方針で置き換えるのかが依頼から判断できない場合
