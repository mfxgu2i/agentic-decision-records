# 決定記録の作成と更新

プロジェクトにおいて「何を、なぜ決めたのか」を明確に残す決定記録です。複数の選択肢から1つを選定した経緯、修正せず受け入れると判断した制約、あえて行わないと決めた方針、検討して採用を見送った案、議論中の論点と結論が出るまでの暫定的な取り決めを記録します。

## ステータス

| status | 意味 | 移行先 |
|---|---|---|
| `proposed` | 結論がまだ出ていない論点。結論が出るまでの間に守る取り決めがあれば、それも含める | `accepted`、`rejected` |
| `accepted` | 確定した決定事項。複数の選択肢から1つを選んだ方針、あえて直さず受け入れた制約、あえて行わないと決めた方針など | `deprecated`、`superseded` |
| `rejected` | 検討したうえで採用を見送った案、または不要になった論点 | なし |
| `deprecated` | 後継の方針なく廃止した決定事項 | なし |
| `superseded` | 新しい決定記録に置き換えられた決定事項 | なし |

新規作成で使えるのは `proposed`、`accepted`、`rejected` です。`deprecated` と `superseded` は、既存の記録のステータスを変更するときにだけ使います。索引への掲載方法は、`SKILL.md` の「記録を作成する」の手順5に従います。

本文を書き換えてよいのは `proposed` の間だけです。`accepted` と `rejected` になった後は本文を書き換えず、ステータスの変更に伴う frontmatter の更新だけを行います。いつ、何を決定したかという経緯がそのまま残されていることに価値があるためです。

## 記録を作成する

保存先は `docs/decisions/NNNN-<kebab-case>.md` です。
ファイル番号は `docs/decisions/` 内の最大番号に1を加え、4桁でゼロ埋めします。最初の1件は `0001` です。

```markdown
---
description: "<どんな作業の前に参照すべきかを1文で簡潔に記述>"
status: accepted
date: <accepted か rejected になった日付。proposed の間は記録を作成した日付 YYYY-MM-DD>
---

# <結論を明確に言い切る見出し>

## 背景

<なぜ決定が必要だったか。確認した事実には、いつどのような方法で確かめたかを明記する>

## 検討した選択肢

| 選択肢 | 評価 |
|---|---|
| <選択肢> | <選定した理由、または採用を見送った理由> |

## 決定事項

<具体的に何を決定したか>

## 影響

<この決定によって得られる利点、引き受けるトレードオフや不利益、今後の作業で遵守すべき事項>
```

- 見出しは「〜する」「〜しない」のように結論を言い切る表現にします。「〜について」のような曖昧な表現は避けます。索引にはこの見出しが掲載され、エージェントは見出しから結論を把握します
- 決定の理由や見送った代替案が会話や文脈から読み取れない場合は、推測で補填せずユーザーに確認します。理由が記録されていない決定事項は、後から変更してよいかの判断が困難になります
- 選択肢の比較を行わずに決定した場合は、「検討した選択肢」のセクションを省略します
- frontmatter は `description`、`status`、`date` の順に記載し、ステータスに応じて追加する項目はその後に配置します

### 議論中の論点

結論がまだ出ていない論点を記録する場合は、上記の雛形を次のように変更します。

| 項目 | 記載方針 |
|---|---|
| `status` | `proposed` |
| 見出し | 「〜を決める」のように、何を決めようとしているかが分かる表現にする |
| 検討した選択肢 | 候補として挙がっている案と、それぞれの現在の評価 |
| 決定事項 | 結論が出るまでの間に守ることがあれば書く。なければ「未定」とだけ書く |
| 影響 | 暫定的な取り決めによって引き受ける不利益。取り決めがなければ省略する |

`proposed` の間は、候補や評価、暫定的な取り決めが変わるたびに、本文を最新の状態に上書きします。議論の経過を追記する節は設けません。経過は Git の履歴に残ります。見出しや `description` を変えた場合は、索引の行も合わせます。
担当者や期限は記録しません。それらを管理する必要がある場合は課題管理ツールを使います。

### 採用を見送った案

`proposed` を経ずに、採用を見送った案を記録する場合は、`status` を `rejected` にします。見出しには案の内容を書き、「決定事項」のセクションに見送った理由を書きます。

## ステータスを変更する

### 論点が決着した

`proposed` の記録を、同じファイルのまま更新します。

| 結論 | 更新内容 |
|---|---|
| 候補のどれかを採った | `status` を `accepted` にし、見出しと「決定事項」「影響」を採った結論に合わせて書き直す |
| どの候補も採らないと決めた | `status` を `accepted` にし、見出しを「〜しない」「今のまま〜を続ける」のような結論に、「決定事項」「影響」をそれに合わせて書き直す |
| 候補が1つの論点で、それを見送った | `status` を `rejected` にし、見出しを案の内容に、「決定事項」を見送った理由に書き直す |
| 論点そのものが不要になった | `status` を `rejected` にし、見出しは論点のまま残す。「決定事項」に不要になった理由を書く |

`rejected` は、論点から結論として残すものが無かったことを表します。「〜しない」と決めた場合は、それを結論として `accepted` にします。

いずれの場合も `date` を決着した日付に更新します。`description` は論点のために書いた文なので、結論に照らして参照すべきタイミングが変わっていないかを見直します。最後に、索引の行を新しいステータス、見出し、`description` に合わせます。`rejected` にした場合は、索引から行を削除します。

### 決定事項を別の方針に変える

後継の方針がある場合は、新しい決定記録で置き換えます。

1. 新しい決定記録を作成します。背景セクションに旧記録への相対リンクと、方針を変更する理由を明記します
2. 旧記録の frontmatter の `status` を `superseded` に変更し、`date` の後ろに `superseded_by: NNNN-xxx.md` を追加します。`description` は、経緯を確認したいときに参照するものだと分かる記述に修正します。本文は変更しません
3. 索引 `docs/decisions/index.md` から旧記録の行を削除し、新しい決定記録の行を追加します

ほかの決定記録から旧記録へ張られているリンクを張り替える必要はありません。リンクは当時の経緯として残し、参照者は旧記録の `superseded_by` から新しい決定記録をたどります。

### 決定事項を廃止する

後継の方針を決めずにやめる場合は、新しい記録を作らず、旧記録のステータスだけを変更します。

1. frontmatter の `status` を `deprecated` に変更し、`date` の後ろに `deprecated_reason: "<廃止した日付 YYYY-MM-DD> <廃止した理由>"` を追加します。理由は1文で書きます。`description` は、経緯を確認したいときに参照するものだと分かる記述に修正します。本文は変更しません
2. 索引から行を削除します

`accepted` を `rejected` に変更する操作はありません。一度採用した決定事項をやめる場合は、廃止するか置き換えます。
