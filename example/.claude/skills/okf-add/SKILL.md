# okf-add — 文書追加ワークフロー

バンドルに知識を1件追加する。本体・索引・履歴をワンセットで更新し、
全 .md に非空 `type` を持たせる OKF v0.1 適合を保つ。

執筆・更新の規約は本書が持つ。バンドル側の `AGENTS.md` はバンドルを読むための構造説明であり、
書き方の規約は持たない。壊してはならない OKF §9 適合条件:

1. 予約ファイルの `index.md` / `log.md` 以外のすべての知識文書は YAML frontmatter と
   空でない `type` を持つ。`AGENTS.md` / `CLAUDE.md` は運用ファイルなので対象外で、索引にも載せない
2. `index.md` に frontmatter を書かない。唯一の例外はバンドルルート `index.md` の
   `okf_version: "0.1"` 宣言。OKF §11
3. `log.md` は `## YYYY-MM-DD` の日付見出しを新しい順に並べ、箇条書きを続ける。既存行は追記のみ
4. ページ間リンクはバンドルルート絶対パス。`[XXX仕様](/specs/xxx-spec.md)` のような形式
5. 文書を追加・改名・削除したら、本体とルート `index.md`、`_references/` の場合は
   当該ディレクトリの `index.md`、そして `log.md` をワンセットで更新する

## バンドルルートの特定

まずカレントディレクトリに`index.md`と知識文書ディレクトリがあればそこがバンドルルート。
なければGlobで`**/knowledge/index.md`を探して特定する。
バンドルのディレクトリ名を`knowledge/`から変えた場合はこのパターンを更新すること。
`okf-query` と `okf-lint` のパターンも合わせて更新する。

## 手順

### 1. 収録すべき内容か確認する

追加しようとしている内容が、コードやREADME等の一次情報を読めば分かることの言い換えに
留まっていないか確認する。該当する場合は追加を保留し、意図をユーザーに確認する。
あえて記録したい理由があるかもしれないため、機械的に拒否はしない。
このBundleに向いているのは、コードには残らない情報。意思決定とその理由、
未解決の問題、調査ログ、コードには残らない運用手順を指す。
仕様書に `type: Specification` を付けて書く場合も、事実の列挙ではなく
「なぜその仕様にしたか」を主体に書く。

コード事実の写経は、コードが変わった瞬間に陳腐化する。バンドルとコードが矛盾したら
コードを正とする以上、写しは構造上いつでも信用できない。

同様に、フレームワークの一般的なベストプラクティスなど、モデルが訓練データとして
既に持っている一般知識も書かない。書くのはこのプロジェクト固有の判断・経緯に絞る。

人間が仕様を一覧で読めるようにしたい場合も、散文で写しを作らない。API・スキーマのように
構造化できるものは`_references/`にOpenAPI / JSON Schema等の実体を置き、手順3で扱う。
知識文書は`resource:`でそれを指すポインタと、判断・落とし穴に絞る。

### 2. トピックの単一性を確認する

追加しようとしている内容が複数の主題にまたがっていないか確認する。またがっている場合は
主題ごとに文書を分割し、以降の手順を文書ごとに繰り返す。OKFは1ファイル1トピックを前提としており、
`okf-query`の「索引→grepで絞る→該当文書を全文read」という段階的絞り込みは、1文書が
1トピックで完結していることに依存している。

### 3. 置き場所を決める

- ルート`index.md`のセクション構成を見て、内容が合うセクションに対応するトピックディレクトリに置く
- 合うセクションがなければ、トピックディレクトリと索引セクションを新設してよい
- 非Markdownファイル、たとえばYAML・PDF・画像は`_references/`に実体を置き、それを説明する
  コンセプト文書の .md を内容に応じたトピックディレクトリに作る

ファイル名はケバブケース英語に、内容種別を表すサフィックスを付ける。`-spec` / `-procedure` など。
`example-spec.md` のような形式にする。`index.md` / `log.md` という名前は予約済みなので使わない。

### 4. frontmatter を付ける

```yaml
---
type: <種別>                        # 必須。下記の語彙を参照
title: "<表示名>"
description: "<一文の要約>"
resource: <対象資産のURI>            # 実体ファイル・外部資産を説明する文書のみ
tags: [<tag>, ...]
timestamp: <YYYY-MM-DD>T00:00:00+09:00
---
```

- `type`: 必須。内容を表す短い英語で自由に定義してよい。OKF に中央登録はない。表記ゆれを
  防ぐため、まずバンドル内の既存語彙をgrepで確認して再利用を検討する。
  開発ナレッジの場合の例: `Decision` / `Specification` / `Investigation` / `Runbook` / `Note` / `Reference`
- `description`: 一文。索引エントリの説明文としてそのまま使うので、単独で意味が通ること
- `timestamp`: 追加日の ISO 8601。`+09:00` を付ける
- `resource`: `_references/` の実体や外部資産を説明する文書のみ。`resource: /_references/xxx.yaml` のような形式

### 5. 本文を書く

- 見出し・リスト・表・コードブロックなど構造的な Markdown を優先する
- 既存コンセプトに言及するときはバンドルルート絶対リンクを使う: `[XXX仕様](/specs/xxx-spec.md)`
- まだ存在しない文書へのリンクは張ってよい。OKF ではリンク切れは「未執筆の知識」として許容される

#### Citations — 出典を要する主張があれば必須

判定は `type` ではなく本文が何を主張しているかで行う。次のいずれかに由来する記述が
あれば、文書末尾に `# Citations` を置き、根拠を番号付きで列挙する。本文の該当箇所には
`[1]` を添える。Agentが「この記述の根拠はどこか」を機械的に取り出せる状態を保つのが目的:

- 一次資料 — `_references/` 配下の資産、外部URL
- 一次観測 — 実機検証・ログ・DBクエリ結果など、いつ・何を観測したか
- 意思決定の経緯 — その判断がいつ・どこで確定したか
- 未確認の推測 — 根拠が無いことを明示する。`[3] 推測。公式仕様は未確認` のような書き方

コードは出典に挙げない。コードが根拠になる主張は手順1の収録方針に反しているので、
Citationsを足すのではなく記述自体を見直す。「変換規則は `xxx()` にある」のような
次にどこを見るかを示すポインタは本文に書いてよい。案内であって根拠ではないため。

バンドル内で自己完結する文書、たとえば用語定義・方針宣言・他文書への索引には不要。

```markdown
# Citations

[1] `/_references/menu-api.yaml` — エンドポイント定義の実体
[2] 実機検証(YYYY-MM-DD) — キャッシュヒットの観測結果
[3] 推測。外部仕様としては未確認
```

### 6. 索引を更新する

- ルート `index.md` の該当セクションに、ファイル名順の位置へ挿入する:
  `* [タイトル](/specs/xxx.md) - <frontmatter の description と同文>`
- `_references/` に置いた場合は `_references/index.md` にも同様に追加する。
  それ以外のディレクトリにはディレクトリ別 `index.md` を置かない
- 新しい種類の知識でセクションが必要になったら `# 見出し` を新設してよい

### 7. log.md に記録する

当日の `## YYYY-MM-DD` 見出しの下に追記する。見出しがなければファイル先頭 `# Log` の直後に新設する:

```
* Creation: [タイトル](/specs/xxx.md) を追加。<一言の背景>
```

既存行は変更しない。日付見出しは新しい順を保つ。

### 8. 自己検査

追加・更新したファイルについて確認する:

- [ ] 本文がコード事実の言い換えに留まっていない。意思決定・未解決課題・調査ログ等の要素がある
- [ ] モデルの一般知識、たとえば一般的なベストプラクティスの解説になっていない
- [ ] 構造化できる仕様を散文で写していない。実体は`_references/`に置いたか
- [ ] `# Citations` にコードを出典として挙げていない
- [ ] 新規 .md に frontmatter と非空 `type` がある
- [ ] 索引エントリの説明文が frontmatter `description` と一致している
- [ ] 張ったバンドル内リンクのパスが実在する。意図的な未執筆リンクは除く
- [ ] log.md の日付見出しが `YYYY-MM-DD` 形式で新しい順

## エスカレーション

次の場合はユーザーに確認してから行う:

- 既存文書との重複が疑われる場合。統合するか別文書にするかの判断が要る
- 既存文書の削除・改名を伴う場合
- 既存文書の大幅な書き換えを伴う場合
